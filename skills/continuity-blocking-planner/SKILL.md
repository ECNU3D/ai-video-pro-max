# 连续性与 Blocking 规划器

## Overview

把剧情已经确定下来的片段，进一步整理成“角色站哪、往哪走、镜头从哪边看、人物和场景布局怎么在逐镜之间保持稳定”的连续性规划文档。

核心原则：先把空间关系和镜头衔接画顺，再下放到平台提示词。默认输出的是连续性与 blocking 规划，不是最终平台 prompt。

这里的“连续性”不只指抽象的轴线正确，也包括更落地的逐镜布局稳定性：

- 谁在画面左 / 右
- 谁靠门 / 靠窗 / 靠玻璃 / 靠墙
- 谁坐桌子哪一侧
- 哪个物件在前景 / 中景 / 背景
- 上一镜建立的布局，下一镜有没有明确继承

生成前先阅读：
- `references/blocking-template.md`：固定输出结构与表格
- `references/continuity-checklist.md`：轴线、锚点、视线、动接、越轴与逐镜布局检查清单

## Scope Decision

优先处理最容易出连续性问题的单位：

1. 单场戏：
默认最佳输入单位，直接做完整 blocking。

2. 一组连续场次：
只有在角色和空间连续相接时才放在同一份文档里。

3. 整集：
不要整集一次性细做 blocking。先拆出重点戏、对话戏、追逐戏、群戏分别处理。

如果用户只给了剧情梗概，没有角色动作、场景入口、主要互动对象等基本信息，先输出“需要补充的 blocking 信息”，不要假装已经可以完成精确规划。

## Workflow Overview

按下面顺序执行：

1. 明确当前处理的空间与戏份边界
2. 读取导演蓝图、剧情文本或平台分镜
3. 搭建空间骨架与固定锚点
4. 规划角色初始站位、世界方位与屏幕方位
5. 规划阶段性走位与情绪节点
6. 选择并锁定轴线策略
7. 设计镜头间的衔接锚点与重置镜头
8. 逐镜审计人物与场景布局是否稳定继承
9. 标出需要合理越轴或禁止越轴的地方
10. 输出连续性与 blocking 规划并要求人审

## Preferred Inputs

理想输入优先级如下：

1. `storyboard-blueprint` 输出的导演分镜蓝图
2. 单场戏剧本 / 文字分镜
3. 已有平台分镜脚本
4. 场设、角色图、走位图、导演示意图
5. 场景参考图 / 空场图 / 俯视示意图 / 机位草图

如果用户提供了场景参考图、空场图、俯视图或机位草图，优先把它们当成布局证据，而不是只凭文字猜。

如果没有图，再根据文字描述推测，并在文档里明确标出：

- 哪些是从文字能确定的
- 哪些只是合理推测
- 哪些因为缺图仍然存在布局漂移风险

如果同时拿到多个来源，以导演蓝图为主，平台分镜脚本为参考，不要反过来让平台写法支配 blocking 判断。

## Step 1: Build The Spatial Skeleton

先把当前场景抽象成可讨论的空间骨架：

- 主要区域：门口、桌边、窗边、楼梯口、道路、掩体、车辆内外
- 固定锚点：门、柱子、桌子、窗户、玻璃、树、石碑、路口、车辆、关键道具
- 出入口与运动方向：谁从哪里来，往哪里去
- 观众最容易迷失方向的位置
- 最容易导致人物“看起来突然换边”的镜头类型

如果空间关系模糊，要主动给出简化版区域命名，例如：

- `A 区` 门口
- `B 区` 中央活动区
- `C 区` 窗边 / 高处 / 掩体后

如果用户给了场景图，还要额外写清：

- 世界锚点：靠门侧 / 靠玻璃侧 / 靠窗侧 / 靠墙侧
- 画面锚点：左前景 / 右前景 / 画面中央 / 背景通道
- 哪些锚点在后续镜头中必须被反复继承

## Step 2: Place Characters Before Cameras

先定角色，再定机位。必须先写清楚：

- 初始站位
- 当前强弱关系
- 当前视线关系
- 谁主动、谁被动
- 谁是本场主对话人 / 主行动人 / 主追击者
- 每个角色在世界空间中的方位
- 每个角色在建立镜头中的屏幕方位

对于多人戏和群戏，要主动降维处理：

- 一人对两人：标记主回应者与次回应者
- 一人对一群：在群体中挑 1 个主说话者和 2-3 个辅助角色
- 群体对群体：先划分阵营，再选阵营代表

对于双人对话或双人对峙，必须至少锁定两套信息：

- 世界方位：谁靠门、谁靠窗、谁靠桌子的哪一侧
- 屏幕方位：在建立镜头里谁在画面左，谁在画面右

## Step 3: Plan Blocking By Beat

blocking 不是全程流水账，而是按戏剧节点分阶段规划。

每个阶段都要说明：

- 角色所在区域
- 谁移动，谁不动
- 移动目的是什么
- 走位会不会改变强弱关系
- 走位是否触发新的轴线
- 哪个动作是下一个镜头的衔接锚点
- 这一阶段建立的布局，下一阶段应该如何继承
- 哪些镜头虽然没人移动，但可能因为机位描述不清导致人物“看起来换边”

当角色发生明显站位变化时，必须考虑是否需要：

- 全景 / 俯视重置镜头
- 过肩镜头
- 主观 / 越肩确认视线
- 物件或空镜过渡

即使角色没有移动，只要存在以下情况，也要主动做“布局稳定性审计”：

- 从全景切到正反打
- 从外视角切到内视角
- 从正拍切到过肩
- 角色直视镜头后切回对视
- 平台提示词里只写了“近景 / 正反打 / 对坐”，没写清谁在哪边

## Step 4: Choose The Axis Strategy

至少判断并写清楚当前使用的是哪类轴线：

- 场景轴线
- 运动轴线
- 关系轴线
- 群体轴线

判断规则：

- 对峙、双人对话：优先关系轴线
- 明确前进目标、追逐或穿越空间：优先运动轴线
- 大场景、阵营对立、多人整体：优先场景轴线或群体轴线

必须明确记录：

- 轴线基于什么主体建立
- 摄像机主要站在哪一侧
- 左右关系应如何保持稳定
- 世界锚点和屏幕锚点的对应关系
- 哪些镜头必须承担“锁定布局”的职责

## Step 5: Design Continuity Bridges

为防止“看不懂”“接不顺”，主动设计衔接桥梁。至少检查：

- 运动趋势衔接
- 锚定元素衔接
- 视线衔接
- 遮挡 / 露出衔接
- 声音或环境衔接
- 运镜衔接

默认优先使用最容易让观众理解空间的方式，不要为了花哨而牺牲清晰度。

如果前后镜头发生这些情况，通常需要桥梁镜头：

- 角色突然换边
- 镜头从室内切到室外
- 对话对象改变
- 角色大幅移动到新区域
- 追逐双方距离显著变化
- 同一场对坐戏里，人物在提示词里没有明确坐哪边
- 建立镜头说明了布局，后续近景 / 特写却没有明确继承方式

## Step 6: Audit Layout Stability Shot By Shot

这一轮是新增的必做步骤。不要只写“大方向上没问题”，要逐镜检查人物与场景布局是否稳定连贯。

至少输出两张表：

1. `布局锁定表`
明确：
- 建立镜头是谁
- 谁在世界空间的哪一侧
- 谁在屏幕空间的哪一侧
- 哪些场景锚点是必须重复出现的

2. `逐镜布局审计表`
逐镜检查：
- 当前镜头是否明确人物屏幕方位
- 当前镜头是否明确人物世界方位
- 当前镜头是否继承上一镜布局
- 当前镜头是否缺少锚点导致平台可能自由换边
- 是否需要给平台 prompt 补最小描述

以下情况默认判为高风险：

- 建立镜头有左右关系，后续镜头完全不写
- 只写“正反打”“近景”“对坐”，不写站位继承
- 只写人物，不写门、桌、窗、玻璃、道具这些场景锚点
- 提示词中的机位站位可能让人物相对位置翻转

如果用户给了场景参考图，要优先按图审核；如果没有，就按文字做推断，并把不确定性写明。

## Step 7: Handle Crossing Deliberately

默认目标是不让观众迷路，不是机械禁止越轴。

如果需要越轴，必须明确采用哪种合理越轴方式：

- 空景 / 物件越轴
- 跟随摇镜越轴
- 场景切换越轴
- 先骑轴，后越轴
- 角色走位越轴

如果没有清晰理由，不要越轴。

如果存在以下情况，优先标记为“禁止越轴”：

- 重要对话戏
- 多人对话刚建立空间关系时
- 观众还没吃透站位时
- 平台分镜后续会进一步压缩镜头时

## Step 8: Output Rules

严格按 `references/blocking-template.md` 的结构输出。

默认文件名：

- `{标题}-连续性与Blocking规划.md`

如果没有明确标题，可用：

- `连续性与Blocking规划.md`

文档必须包含：

- 场景空间骨架
- 初始站位表
- 布局锁定表
- 分阶段走位表
- 逐镜布局审计表
- 轴线策略
- 衔接锚点设计
- 越轴处理方案
- 风险清单
- 下游交接建议

## Review Gate

输出后先让用户审阅，重点确认：

- 空间是否好理解
- 角色左右关系是否符合预期
- 人物布局是否在逐镜之间稳定连贯
- 世界方位和屏幕方位是否都讲清楚
- 关键走位是否需要改
- 哪些越轴是刻意保留，哪些应该删

明确提醒：

- 这是一份 blocking 与连续性文档，不是最终平台提示词
- 如果通过，可交给 `dialogue-scene-director`、`action-scene-choreographer` 或各平台分镜技能继续落地

## Quality Bar

以下情况视为失败：

- 只有镜头建议，没有空间骨架
- 没有初始站位和阶段走位
- 没有布局锁定表或逐镜布局审计
- 没有轴线策略
- 没有锚点镜头或衔接桥梁
- 需要越轴却没说明方法
- 直接把 blocking 文档写成平台 prompt
- 没有指出哪里最可能让观众看不懂
