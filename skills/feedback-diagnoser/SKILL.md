# 反馈诊断器

## Overview

把模糊反馈先翻译成可执行的诊断结论，再决定应该微调 prompt、重排镜头，还是回退到更上游的导演设计层。

核心原则：不要一拿到“感觉不对”就直接改 prompt。先判断问题发生在哪一层、影响范围有多大、最省成本的修法是什么。默认输出的是“反馈诊断与修正路径”文档，不是直接重写分镜。

生成前先阅读：
- `references/diagnosis-template.md`：固定输出结构
- `references/symptom-map.md`：常见反馈症状与归因路径

## Scope Decision

优先处理“一个明确反馈对象”，不要把整条生产链混在一起诊断。

可处理的对象包括：

1. 单场戏 / 单段分镜
2. 一份导演蓝图或 blocking 文档
3. 一份平台分镜脚本
4. 一次生成结果及其反馈
5. 一组修改意见

如果用户同时给了多个文件和多轮反馈，先按“最痛的那一处”聚焦，避免一次把所有问题都揉成一锅。

## Workflow Overview

按下面顺序执行：

1. 锁定反馈对象与当前版本阶段
2. 把模糊反馈翻译成可验证症状
3. 判断问题更可能发生在哪一层
4. 评估修改范围与返工成本
5. 给出最优修正路径和下一技能建议
6. 输出供人审阅的诊断文档

## Preferred Inputs

理想输入优先级如下：

1. 原始反馈原文
2. 被反馈的对象：蓝图 / blocking / 分镜脚本 / 生成视频
3. 对应的上游文档：`storyboard-blueprint`、`continuity-blocking-planner`、`dialogue-scene-director`、`action-scene-choreographer`
4. 用户当前最在意的问题和成本约束

如果只有一句模糊反馈，没有任何上下文，先输出“当前无法精确诊断的原因”和“需要补充的最小信息”。

## Step 1: Identify The Current Stage

先判断问题出现在创作链的哪一层：

- 剧情 / 蓝图层
- 节奏规划层
- 连续性 / 走位层
- 对话设计层
- 动作设计层
- 氛围 / 风格层
- 平台分镜 prompt 层
- 生成执行层

同一句“这段不太对”，落在不同阶段，处理方式完全不一样。

## Step 2: Translate Feedback Into Symptoms

把口语反馈改写成可检验的症状，避免空泛复述。

例如：

- “太平” 不等于一个问题，可能是构图太平、流水账、情绪太平
- “看不懂” 不等于观众笨，可能是故事没画顺、锚点缺失、动接断裂
- “感觉不对” 不等于只能靠直觉，可能是节奏、表演、氛围、运镜或风格错位

每条反馈至少拆成：

- 原始说法
- 译成专业症状
- 当前可见证据
- 还缺什么证据

## Step 3: Diagnose By Layer, Not By Mood

优先从以下层级做归因，不要一上来就怪平台：

1. 信息完整度层：
是否缺 5W2H，导致根本无法画清楚。

2. 剧情重点层：
是否没提炼重点，导致像流水账。

3. 构图 / 空间层：
是否缺纵深、主次、空间压力、重点视线。

4. 衔接 / 连续性层：
是否角色进出场、锚点、动接、左右关系没交代清楚。

5. 节奏层：
是否时长、张弛、快慢分布不对。

6. 表演 / 情绪层：
是否角色动作、表情、语速、气场没有打中剧情需求。

7. 氛围 / 风格层：
是否光影、色调、环境气质、音乐感想象跑偏。

8. 专项设计层：
对话戏是否不够有戏，动作戏是否不够成立、不够升级。

9. 平台执行层：
是否 prompt、首尾帧、平台能力边界导致落地偏差。

## Step 4: Rank Root Causes

不要只给一个武断结论。至少输出前 3 个最可能原因，并说明：

- 为什么怀疑它
- 证据来自哪里
- 影响范围有多大
- 修复优先级为什么排在这里

如果存在“上游没定好，导致下游怎么改都别扭”的情况，必须明确写出来。

## Step 5: Estimate Change Radius

每次诊断都要判断该改多大，不然很容易过修。

使用以下四档：

- `L1 微调`：单镜头词汇、单处衔接、局部氛围修正
- `L2 段落调整`：一个动作段落、一个对话段落、几个镜头的重排
- `L3 场次重构`：需要回到蓝图 / blocking / 节奏设计层重做
- `L4 上游返工`：剧本、角色、地形、资产条件本身有问题，需要先沟通或补信息

## Step 6: Route To The Right Fix Path

诊断的目标不是“显得懂很多”，而是给出最省成本的下一步。

常见路由如下：

- 剧情重点不清 / 流水账：回到 `storyboard-blueprint`
- 景别、时长、张弛不对：回到 `shot-rhythm-planner`
- 看不懂 / 走位乱 / 越轴 / 动接断：交给 `continuity-blocking-planner`
- 对话场不够有戏 / 表演不对：交给 `dialogue-scene-director`
- 武戏不够爽 / 不成立 / 不升级：交给 `action-scene-choreographer`
- 氛围不对 / 光影不对 / 气质不对：交给 `scene-atmosphere` 或 `visual-director`
- 首尾帧迁移 / 词图不一致：交给 `video-transition-auditor`
- 已经明确是平台 prompt 表达问题：再交给各平台 storyboard 技能修订

## Step 7: Output Rules

严格按 `references/diagnosis-template.md` 的结构输出。

默认文件名：

- `{标题}-反馈诊断.md`

如果没有明确标题，可用：

- `反馈诊断.md`

文档必须包含：

- 反馈对象与当前版本阶段
- 原始反馈翻译
- 根因排序
- 修改范围等级
- 修正路径建议
- 需要补充的信息

## Review Gate

输出后先让用户审阅，重点确认：

- 诊断的“问题层级”是否说中了
- 修改范围是否符合当前时间和成本
- 是否接受先修上游，而不是继续盲调 prompt
- 下一步要交给哪个技能继续处理

明确提醒：

- 这是一份反馈诊断文档，不是最终修订稿
- 如果通过，再交给对应技能进入真正修改

## Quality Bar

以下情况视为失败：

- 只是复述用户反馈，没有翻译成专业症状
- 直接给笼统建议，如“再大气一点”“再燃一点”
- 没有区分设计层问题和平台执行层问题
- 没有判断修改范围
- 没有给出下一技能路由
- 明明是上游问题，却让用户继续下游盲改
